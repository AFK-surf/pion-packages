# Red-team audit: `packages/markdown` (`d082835`) vs Rust `pulldown-cmark 0.13.1`

Target: `origin/feat/opt-markdown` @ `d082835` ("zero-Event streaming HTML…"). The oracle is the real
crate pinned to `=0.13.1` (`audit/rust_ref/Cargo.lock`), built with `--release`. Machine: Darwin arm64
(tokyo-mac-studio-0), `pionc 0.1.0 (arm64_apple, self-hosted)`, `cargo 1.100.0`.

Nothing under `packages/markdown/src/**`, the existing tests, or the repo root was changed. Everything in
this audit lives under `packages/markdown/audit/`.

## Reproduce

```sh
export PATH="$HOME/.pion/bin:$HOME/.cargo/bin:$PATH"
pionc test -p markdown_redteam packages/markdown/audit   # 81 tests: 73 FAIL (= evidence), 8 ok_ guard rails pass
sh packages/markdown/audit/run_audit.sh                  # full run, about 5 min (QUICK=1 for about 1 min)
```

`run_audit.sh` builds the oracle (`audit/rust_ref`) and the Pion harness (`audit/harness`, which calls
`to_html_pulldown`, `render_html_pulldown(parse())`, `to_html` and `render_html(parse())` on the same
input). It then runs these steps:

1. the red-team tests;
2. a three-way differential over all 1148 inputs from pulldown-cmark's own `tests/suite/*.rs`, plus about 140
   hand-written attack cases (`scripts/corpus.py`) and 20,000 seeded fuzz documents, each under 3 option
   sets. Divergences are reduced by batch delta-debugging (`scripts/minimize.py`) and grouped by
   `scripts/classify.py`;
3. pulldown-cmark's own test suite scored on Pion (`scripts/suite_score.py`);
4. DoS probes;
5. a scaling benchmark over 50 pathological generators (`scripts/patho_bench.py`);
6. `scripts/bench_compare.py` runs. Their SHA-256 must match, so pathological inputs are only put through it
   when both outputs are byte-identical.

All generated files go to `$AUDIT_TMP` (default `$TMPDIR/pion-markdown-audit`).

`audit/tests/redteam_test.pion` is generated by `scripts/gen_tests.py`. The expected bytes come from the
oracle when the file is generated. GFM-spec cases have their expected output written inline.

## P0: crashes, super-linear DoS, the two render paths disagreeing, structurally wrong HTML

### P0-1 Stack overflow (SIGSEGV) on small nested input, in both render paths

| input | size | Rust | Pion `to_html_pulldown` | Pion `parse()`+render |
|---|---:|---|---|---|
| `"> " * 50000 + "a"` | 100 KB | ok | **SIGSEGV (rc 139)** | **SIGSEGV** |
| `"- " * 32000 + "a"` | 64 KB | ok | **SIGSEGV** | **SIGSEGV** |
| `"1. " * 32000 + "a"` | 96 KB | ok | **SIGSEGV** | **SIGSEGV** |
| `"> " * 10000`, `"- " * 20000` | 20–40 KB | ok | ok | ok |

- **Reproduce:** `run_audit.sh`, step 5. To run one case by hand:
  `python3 -c "print('> '*50000+'a')" > x.md && $T/pion_harness direct x.md 0; echo $?` prints `139`.
- **Impact:** about 100 KB of untrusted Markdown kills the process. A library has no way to catch this.
- **Likely cause:** block nesting depth maps one-to-one onto native recursion: `render_block_direct`
  (`src/inlines.pion:1832`, self-calls at :1894/:1952/:2051/:2083), `emit_block_events` (:2403), and the
  block parser. There is no depth cap. pulldown-cmark walks its tree iteratively.
- These cases are not in `redteam_test.pion`, because a SIGSEGV would take down the whole `pionc test` process.

### P0-2 Super-linear inline algorithms (Rust stays linear)

From `patho_bench.py`. *k* is the fitted exponent in time ∝ bytes^k, taken between the two largest sizes.
Every row has byte-identical output unless noted.

| generator (N) | input | Rust | Pion direct | Pion events | k Rust / Pion | slowdown |
|---|---:|---:|---:|---:|---:|---:|
| `*a **a `×N `b` ` a** a*`×N (cmark pathological #1), N=16000 | 224 KB | 7.0 ms | **6019 ms** | 6230 ms | 0.48 / **2.03** | **858×** |
| same, N=32000 (Rust at N=128000, 1.8 MB: 30.5 ms) | 448 KB | — | **>30 s (timeout)** | timeout | | |
| `"'`×N `a` `'"`×N (smart quotes), N=16000 | 64 KB | 5.5 ms | **1039 ms** | 1056 ms | 0.13 / **2.00** | **188×** (outputs differ only in quote direction) |
| `</` + `<!--`×N (unclosed comments), N=16000 | 64 KB | 5.4 ms | **280 ms** | 279 ms | 0.40 / **1.84** | **52×** |
| same, N=128000 | 512 KB | 11.7 ms | **>30 s (timeout)** | | | |
| `- `×N (inline list nesting), N=16000 | 32 KB | 5.4 ms | 99.8 ms | 106 ms | 0.33 / **1.58** | 18× |
| backtick runs of growing length (cmark #12) | 1.0 MB | 6.3 ms | 266 ms | 335 ms | 0.45 / **1.5–1.85** | 42× |
| indented list lines (depth ≤ 200), 128k lines | 26 MB | 86 ms | 1148 ms | 1337 ms | linear | **13×** |

The same inputs through `scripts/bench_compare.py` (7 interleaved rounds, SHA-256 identical for all three
implementations):

| input | Rust median | Pion `to_html_pulldown` | Pion `parse`+`render_html_pulldown` |
|---|---:|---:|---:|
| nested strong/emph N=4000 (56 KB) | 12.9 ms | 376.1 ms (**0.03×**) | 378.0 ms (0.03×) |
| unclosed `<!--` N=32000 (128 KB) | 12.8 ms | 1259.7 ms (**0.01×**) | 1260.3 ms (0.01×) |
| increasing backtick runs (500 KB) | 14.0 ms | 100.4 ms (0.14×) | 102.3 ms (0.14×) |
| deeply indented list lines (6.5 MB) | 31.8 ms | 301.2 ms (0.11×) | 309.0 ms (0.10×) |
| inline list depth 16000 (32 KB) | 14.8 ms | 134.4 ms (0.11×) | 139.1 ms (0.11×) |

Root-cause pointers, from reading the code only (nothing was modified):

- **Emphasis:** `process_emphasis` (`src/inlines.pion:344`). After each match it walks
  `found_opener+1..closer_idx` and clears flags, but leaves the entries in `ctx.delims` (the loops at about
  :402 and :520). Every later opener search walks back over all the dead entries again. The `bottoms`
  optimisation only applies to openers that were never found.
- **Quotes:** the `'`/`"` branch searches back linearly from `closer_idx-1` to `stack_bottom` with no
  `bottoms` bound, then runs the same clearing loop.
- **Comments:** `scan_inline_html` (`src/scanners.pion:1047`) re-scans to the end of the input for `-->` at
  every `<!--`. Nothing records "no `-->` after offset X".

**Honest counterpoint:** on `mismatched_openers_closers` (`*a_ `×N, cmark #6) **Rust is the quadratic one**:
3.92 s against 21 ms for Pion at N=128000. Pion is also no slower than Rust on the other 40-odd generators
(brackets, links, tables, refs, entities, …).

### P0-3 `to_html_pulldown` (direct path) ≠ `render_html_pulldown(parse())` ≠ Rust on loose task lists

Input: `- [ ] a\n\n- [x] b\n` with GFM options. Same bug in pulldown's regression #70.

```
Rust / parse()+render : <li>\n<p><input disabled="" type="checkbox"/>\na</p>
Pion direct           : <li><p><input disabled="" type="checkbox"/>\na</p>
```

`to_html` and `render_html(parse())` disagree in the same way. This is the **only** divergence between the
two paths in 63,864 + 21,288 differential cases (`direct!=events(pulldown)`: 4, i.e. this input times 2
masks times 2 renderers). Tests: `p0_paths_loose_tasklist_*`.

### P0-4 Wrong tight/loose decision when a list item starts with indented code (spec violation)

`-     test\n\n  test2\n` → Pion: `…</code></pre>\ntest2</li>` (tight).
CommonMark, cmark, commonmark.js and pulldown all give `<p>test2</p>` (loose). The same happens with
`-     test\n\n- test2\n`. This is wrong in **both** `to_html` (strict CommonMark renderer) and the parse path.
Tests: `p0_list_indented_code_*`.

### P1-2 GFM strikethrough breaks the flanking rules (spec-breaking, not just parity)

| input | Rust | Pion |
|---|---|---|
| `~~ ~~` | `~~ ~~` | `<del> </del>` (opener followed by whitespace is not left-flanking) |
| `a~~ b ~~c` | literal | `a<del> b </del>c` |
| `~~\n~~` | literal | `<del>\n</del>` |
| `~~$~~b`, `~~'~~x`, `~~>~~a` | literal | `<del>$</del>b` (closer preceded by punctuation and followed by alnum is not right-flanking) |
| `This~is~nothing` | literal | `This<del>is</del>nothing` (upstream strikethrough #8) |
| `~This~is~nothing~` | `<del>This~is~nothing</del>` | `<del>This</del>is<del>nothing</del>` (upstream #9) |

The fuzzer reduced 101 distinct inputs into this class. Tests: `p1_strike_*`.

### P1-3 Smart punctuation

- **Bug:** with smart punctuation on, a straight `'` leaks into the output unconverted:
  `*- '*` → `<em>- '</em>`. Rust gives `’`. Also `_> '_` and `*'é*`.
- **Parity:** quote direction differs from pulldown in 71 reduced inputs, including upstream regression #147
  and #179 and spec #508, #622, #632 under smart punctuation. Example:
  `'[foo]'bar` → Pion `‘…’`, Rust `’…’`.

Tests: `p1_smart_*`.

### P1-4 Table block structure

| input | Rust | Pion |
|---|---|---|
| table followed by `*` or `2.` | table, then `<ul>`/`<ol>` | swallows `*` / `2.` as a table cell (GFM: the table ends at another block start) |
| table followed by a line `\|` | table ends, `<p>\|</p>` | adds an empty row |
| `lorem ipsum\nA \| B\n---\|---` | paragraph | interrupts the paragraph with a table (upstream regression #23) |
| `\|\n\|-` | paragraph | empty one-column table |
| `\| Double \| \`\\\\\|\` \|` | table with `<code>\|</code>` | not a table at all (upstream table #18, #22–#26) |

Tests: `p1_table_*`.

### P1-5 Task lists

`- [x]` with nothing after it (also before a nested list or blockquote) renders as literal `[x]`. Rust
renders a checkbox (upstream regression #198, #210). Tests: `p1_tasklist_*`.

### P1-6 The "byte-for-byte `push_html`" claim does not hold

`to_html_pulldown` writes `<li>\n<div>`, `<li>\n<table>`, `<li>\n   <div>`, where pulldown writes
`<li><div>`, `<li><table>` and so on. Affected: spec #175 under the pulldown renderer, and upstream regression
#169 and #171–#174. A trailing tab before a soft break leaks into the output (`b\t\nc` → `b\t\nc`; Rust
gives `b\nc`), which is why 316 reduced inputs land in the tab class. Tests: `p1_pulldown_fmt_*` and
`p1_softbreak_*`.

### P1-7 GFM autolink literals (an option only Pion has), checked against GFM 0.29 spec examples

- `www.google.com/search?q=commonmark&hl;`: the trailing entity is not excluded.
- `ftp://foo.bar.baz` is not linked.
- `a.b-c_d@a.b_` is linked. Per the spec, only `.` may end an address.
- The extended protocols `mailto:foo@bar.baz` and `xmpp:foo@bar.baz` are not supported.

Tests: `p1_gfm_autolink_*`.

### P1-8 Capability gaps against pulldown-cmark 0.13.1's real API

| pulldown-cmark 0.13.1 | Pion `markdown` |
|---|---|
| `Parser` is a lazy `Iterator<Item=Event>` | `parse()` builds an entire `Array[Event]` up front. The event path costs **2× the RSS**: 39.9 MiB vs 20.1 MiB on the GFM corpus, and 53.2 MiB vs 37.3 MiB for Rust on the spec corpus |
| `into_offset_iter()` gives source byte ranges per event (editors, LSP, highlighting) | **none**: `Event` has no position data |
| `BrokenLinkCallback` (`new_with_broken_link_callback`) | **none** |
| `ENABLE_FOOTNOTES` / `ENABLE_OLD_FOOTNOTES` | none, and it fails silently: `[^a]` plus `[^a]: Cool.` renders as `<a href="Cool.">^a</a>`. `![^1]` becomes `<img src="foo">` |
| `ENABLE_HEADING_ATTRIBUTES`, `ENABLE_MATH`, `ENABLE_DEFINITION_LIST`, `ENABLE_WIKILINKS`, `ENABLE_SUPERSCRIPT`/`SUBSCRIPT`, `ENABLE_GFM` (alerts) | none. Math content gets emphasis-parsed (`$a*b*c$` → `<em>`) |
| `ENABLE_YAML_STYLE_METADATA_BLOCKS` / `PLUSES_DELIMITED` | none: front matter renders as `<hr />` + `<h2>` |
| `CowStr` borrows (zero-copy text events) | every `Event::Text` is a newly allocated `String` |

Tests: `gap_*` (10).

|---|---:|---:|---:|

## P2: robustness, and parity divergences where Pion matches cmark or the spec

**Invalid UTF-8.** Pion passes invalid bytes straight through into the "HTML" output, so the output is not
valid UTF-8. `\xff*a*\xc3` → `<p>\xff<em>a</em>\xc3</p>`. A truncated multibyte sequence can also act as an
emphasis flanking character: `**\xe4\xb8**x` → `<strong>`. Rust's `&str` input type rules this input out.
This is not in the Pion tests because a source literal cannot carry invalid UTF-8. See `run_audit.sh`, step 5.

**Parity only.** In the rows below Pion agrees with cmark or the CommonMark spec, and pulldown does something
else. They break the drop-in or byte-identical promise, but they are **not** spec bugs in Pion. Tests: `p2_*`.

| class (reduced inputs) | example | note |
|---|---|---|
| no trailing newline at EOF (463) | `\tcode` → Pion `code\n`, Rust `code` | Pion = cmark |
| CR-only line endings (most of the 178 CR cases) | `` ```\rx `` → Rust treats `x` as the info string | Rust bug |
| CRLF inside a code span or inline HTML | `` `a\r\nb` `` → Rust `a  b` | Pion = spec |
| `'` in href, title or info string | Rust writes `&#x27;` / `&#39;`, Pion writes `'` | harmless inside `"…"` attributes |
| `^` in href | Rust `^`, Pion `%5E` | |
| softbreak in image alt | Rust uses a space, Pion uses `\n` | |
| trailing tab in an ATX heading, tab in a fence info string | Rust keeps it, Pion strips or splits | Pion = cmark |
| `>x\n+` | Rust starts an empty list | Pion = spec (an empty item cannot interrupt a paragraph) |
| 1000-character link label | Rust links it | Pion = spec (labels cap at 999) |
| unmatched `"` under smart punctuation | Rust `“`, Pion `”` | Pion = commonmark.js |
| GFM tagfilter (`<title>`, `<xmp>`, …) | neither implements it | |

**Where Pion is better, recorded for fairness.** U+0000 → U+FFFD, which CommonMark §2.3 requires: Pion does
it, while pulldown-cmark 0.13.1 emits a raw NUL (tests `ok_nul_*`). There is no quote or attribute injection
in any of the 85k differential outputs (`ok_xss_*`). Peak RSS on the direct path is lower than Rust's.

## Summary of evidence

- `redteam_test.pion`: **73 / 81 fail**. P0 6, P1 41, gap 10, P2 16. The 8 `ok_` guard rails pass.
- Differential (default fuzz 20,000): 63,864 cases. Pion direct ≠ Rust in **10,155**; parse path ≠ Rust in
  10,151; direct ≠ parse in **4**. Delta-debugging reduces these to **1,220** unique minimal inputs, in
  `$AUDIT_TMP/diff/min.json`. No Pion crash happened inside the differential corpus; the crashes come only
  from deep nesting (P0-1).
- **Inputs that crash or hang:** 100 KB (SIGSEGV), 224 KB (6 s), 448 KB (>30 s), 512 KB of `<!--` (>30 s).
  Rust handles every one in ≤ 31 ms.
